  CHAPTERS 3 & 4 — FULL REQUEST FLOW DIAGRAM
=============================================

This builds on chapter 3. Chapter 4 adds DynamoDB (the database) to persist jobs.
Before chapter 4, uploads were "fire and forget" — now they're saved and queryable.


WHAT CHANGED IN CHAPTER 4
==========================

Before (Ch 3):  Upload file → store in S3 → return response → job data is lost
After  (Ch 4):  Upload file → store in S3 → save job to DynamoDB → return response
                 Now you can GET /jobs and GET /jobs/{id} and get real data back.

New pieces:
  - store.JobStore interface (internal/api/store/store.go)
  - DynamoDBStore implementation (internal/api/store/dynamodb.go)
  - DynamoDB table "mediaforge-jobs" running in LocalStack
  - main.go now creates the DynamoDBStore and passes it to the Server

==========================================

HOW THE PIECES FIT TOGETHER
============================

┌──────────────┐         ┌──────────────┐         ┌──────────────────┐
│              │         │              │         │                  │
│   Handlers   │────────▶│  Interfaces  │────────▶│  Implementations │
│ (handlers.go)│         │              │         │                  │
│              │         │              │         │                  │
└──────────────┘         └──────────────┘         └──────────────────┘

  s.storage.Upload()  →  storage.Client    →  S3Client → LocalStack S3
  s.store.Create()    →  store.JobStore    →  DynamoDBStore → LocalStack DynamoDB

The handlers only talk to interfaces. They never import or reference S3Client
or DynamoDBStore directly. This means:
  - You can swap implementations without touching handler code
  - You can write tests with fake/mock implementations
  - Each layer has one job and doesn't know about the others

Here's a more simple flow for the SQS and S3 confusion

  FULL FLOW:

  1. Upload file                → S3 (the actual file bytes)
  2. Create job record          → DynamoDB (status: "pending", no metadata yet)
  3. Push jobID to queue        → SQS

  4. Worker picks up message    ← SQS
  5. Worker fetches job info    ← DynamoDB (to know which file, where it is)
  6. Worker downloads file      ← S3
  7. Worker processes it        (extracts metadata, generates thumbnail)
  8. Worker uploads thumbnail   → S3 (a new file)
  9. Worker updates job record  → DynamoDB (status: "complete", adds metadata + thumbnail URL)

  So the answers:

  ┌───────────────────────────────────────┬──────────┬───────────────────────────────────────────────────────┐
  │                Result                 │ Goes to  │                          Why                          │
  ├───────────────────────────────────────┼──────────┼───────────────────────────────────────────────────────┤
  │ Thumbnail                             │ S3       │ It's a file (image bytes), S3 stores files            │
  ├───────────────────────────────────────┼──────────┼───────────────────────────────────────────────────────┤
  │ Metadata (width, height, codec, etc.) │ DynamoDB │ It's data about the job, gets added to the job record │
  └───────────────────────────────────────┴──────────┴───────────────────────────────────────────────────────┘

  Look at your models.Job struct — the fields are already there waiting to be filled in:

  ThumbnailURL string    `json:"thumbnail_url,omitempty"`    // ← worker fills this
  Metadata     *Metadata `json:"metadata,omitempty"`         // ← worker fills this
  Status       JobStatus `json:"status"`                     // ← worker changes to "complete"

  After processing, the worker calls s.store.Update(ctx, job) to write those fields back to DynamoDB. Then when you GET /api/v1/jobs/{id}, you see the complete job with thumbnail URL and metadata.
