MEDIAFORGE — FULL PROJECT FLOW (CHAPTERS 1-7)
===============================================

This document traces the entire lifecycle of the application — from startup
to a completed job — showing how all the pieces connect.


WHAT IS MEDIAFORGE?
====================

A media processing service. Users upload videos/images via an API.
The service stores the file, then asynchronously processes it
(generates a thumbnail, extracts metadata like resolution and duration).
Users can check back later to see the status and results.


STARTUP (runs once when you do `make dev`)
==========================================

┌─────────────────────────────────────────────────────────────────────────┐
│  cmd/server/main.go — runs top to bottom, ONE TIME                      │
│                                                                         │
│  1. Create S3 client                                                    │
│     → configures connection to file storage (LocalStack, port 4566)     │
│     → this is the "toolbox" for uploading/downloading files             │
│                                                                         │
│  2. Create DynamoDB client                                              │
│     → configures connection to the job database (LocalStack, port 4566) │
│     → this is the "toolbox" for saving/reading job records              │
│                                                                         │
│  3. Create SQS client                                                   │
│     → configures connection to the message queue (LocalStack, port 4566)│
│     → this is the "mailbox" between the API and the workers             │
│                                                                         │
│  4. Create video processor                                              │
│     → needs the S3 client (to download videos and upload thumbnails)    │
│     → registered with the worker pool so workers know how to handle     │
│       video jobs                                                        │
│                                                                         │
│  5. Create and start worker pool in the background                      │
│     → launches 1 poller goroutine (asks SQS for messages)              │
│     → launches 3 worker goroutines (process jobs concurrently)          │
│     → all connected via a channel (the pipe between poller and workers) │
│                                                                         │
│  6. Create HTTP server and start listening on port 8080                 │
│     → stores S3 client, DynamoDB client, and SQS client inside          │
│       the Server struct                                                 │
│     → sets up routes (which URL maps to which handler)                  │
│     → BLOCKS HERE — server sits idle, waiting for requests              │
│                                                                         │
│  After this, two things are running concurrently:                       │
│    - The HTTP server (handling requests)                                │
│    - The worker pool (processing jobs in the background)               │
└─────────────────────────────────────────────────────────────────────────┘


UPLOAD FLOW (what happens when someone uploads a file)
======================================================

┌─────────────────────────────────────────────────────────────────────────┐
│  USER sends: POST /api/v1/upload with a file attached                   │
└─────────────────────────────────┬───────────────────────────────────────┘
                                  │
                                  ▼
┌─────────────────────────────────────────────────────────────────────────┐
│  MIDDLEWARE (runs on every request, in order)                            │
│                                                                         │
│  RequestID → stamps the request with a unique ID for tracing            │
│  RealIP → figures out the real client IP (even behind proxies)          │
│  Logger → starts a timer (will log how long the request took)           │
│  Recoverer → catches panics so the server doesn't crash                 │
│  CORS → adds headers so browsers can call this API                      │
│                                                                         │
│  Then matches the URL to a handler:                                     │
│  POST /api/v1/upload → handleUpload()                                   │
└─────────────────────────────────┬───────────────────────────────────────┘
                                  │
                                  ▼
┌─────────────────────────────────────────────────────────────────────────┐
│  handleUpload() — the main upload handler                               │
│                                                                         │
│  1. Parse the uploaded file from the HTTP request                        │
│     → enforces 100MB max size                                           │
│     → extracts the file data, filename, and content type                │
│                                                                         │
│  2. Detect media type                                                   │
│     → checks content type and file extension                            │
│     → determines if it's "video" or "image"                             │
│     → rejects unsupported formats                                       │
│                                                                         │
│  3. Generate a unique job ID                                            │
│     → UUID like "9e4edd29-3b88-4cdc-a250-6dc50e52c4df"                 │
│     → used as the key for everything (S3 path, DB record, queue msg)   │
│                                                                         │
│  4. Upload file to S3                                                   │
│     → stored at: originals/{jobID}.mp4                                  │
│     → the actual bytes go to LocalStack's S3 service                    │
│                                                                         │
│  5. Generate a presigned URL for the original                           │
│     → a temporary download link (expires after 15 minutes)              │
│                                                                         │
│  6. Create job record in DynamoDB                                       │
│     → saves: ID, filename, media type, status (pending), URL, timestamps│
│     → this is where the job is "born" in the database                  │
│                                                                         │
│  7. Send job ID to SQS                                                  │
│     → just the ID string, nothing else                                  │
│     → a worker will pick this up later and process the file             │
│                                                                         │
│  8. Return response to user immediately                                 │
│     → 202 Accepted: "here's your job ID, processing will happen later" │
│     → user is DONE — they don't wait for processing                    │
└─────────────────────────────────────────────────────────────────────────┘

     At this point:
       S3 has: the uploaded file
       DynamoDB has: a job record with status "pending"
       SQS has: a message with the job ID
       User has: a response with the job ID


WORKER FLOW (happens in the background, after upload)
=====================================================

┌─────────────────────────────────────────────────────────────────────────┐
│  POLLER — running in an infinite loop since startup                     │
│                                                                         │
│  Asks SQS: "got any messages?"                                          │
│  → waits up to 20 seconds for a message to arrive (long polling)       │
│  → when a message comes: drops it into the channel                      │
│  → goes back to asking again                                            │
└─────────────────────────────────┬───────────────────────────────────────┘
                                  │
                                  │  message goes through the channel
                                  ▼
┌─────────────────────────────────────────────────────────────────────────┐
│  WORKER — one of 3 goroutines sitting idle, waiting on the channel      │
│                                                                         │
│  Picks up the message and processes it:                                  │
│                                                                         │
│  1. Fetch the job record from DynamoDB                                  │
│     → uses the job ID from the message                                  │
│     → now the worker knows: filename, media type, where the file is     │
│                                                                         │
│  2. Update status to "processing" in DynamoDB                           │
│     → if you query GET /jobs/{id} right now, you'd see this status     │
│                                                                         │
│  3. Find the right processor for the media type                         │
│     → loops through registered processors                               │
│     → asks each one: "do you support video?"                            │
│     → VideoProcessor says yes                                           │
│     → (if none found: marks job as "failed", done)                     │
│                                                                         │
│  4. Run the processor (see VIDEO PROCESSING below)                      │
│     → this is the slow part — downloading, ffprobe, ffmpeg, uploading   │
│     → returns: thumbnail URL + metadata                                 │
│                                                                         │
│  5. Update job in DynamoDB with results                                 │
│     → status: "complete"                                                │
│     → thumbnail_url: the S3 URL for the generated thumbnail            │
│     → metadata: width, height, duration, codec, file size               │
│                                                                         │
│  6. Delete the message from SQS                                         │
│     → tells SQS "I'm done, don't redeliver this"                       │
│     → if the worker had crashed, SQS would redeliver after 30 seconds  │
└─────────────────────────────────────────────────────────────────────────┘


VIDEO PROCESSING (inside the processor, called by the worker)
=============================================================

┌─────────────────────────────────────────────────────────────────────────┐
│  VideoProcessor.Process()                                               │
│                                                                         │
│  1. Create a temp directory on disk                                     │
│     → working space, automatically deleted when done                    │
│                                                                         │
│  2. Download the video from S3 to the temp directory                    │
│     → streams bytes from LocalStack → writes to disk                   │
│     → needed because ffprobe/ffmpeg work with local files, not URLs     │
│                                                                         │
│  3. Run ffprobe on the video                                            │
│     → command-line tool (not Go code — runs as a shell command)         │
│     → reads the video file and outputs metadata as JSON                 │
│     → we parse the JSON and extract: width, height, duration, codec,   │
│       file size                                                         │
│                                                                         │
│  4. Run ffmpeg on the video                                             │
│     → another command-line tool                                         │
│     → seeks to 1 second into the video                                  │
│     → grabs that frame as a JPEG image (the thumbnail)                 │
│     → saves it to the temp directory                                    │
│                                                                         │
│  5. Upload the thumbnail to S3                                          │
│     → stored at: thumbnails/{jobID}.jpg                                 │
│     → now S3 has both the original file AND the thumbnail               │
│                                                                         │
│  6. Generate a presigned URL for the thumbnail                          │
│     → temporary download link for the thumbnail                         │
│                                                                         │
│  7. Return thumbnail URL + metadata to the worker                       │
│     → worker saves these to DynamoDB (step 5 in WORKER FLOW above)     │
│                                                                         │
│  8. Temp directory is automatically cleaned up                          │
│     → the downloaded video and generated thumbnail on disk are deleted  │
│     → the permanent copies live in S3                                   │
└─────────────────────────────────────────────────────────────────────────┘


QUERYING JOBS (what the user does after uploading)
==================================================

┌─────────────────────────────────────────────────────────────────────────┐
│  GET /api/v1/jobs/{id}                                                  │
│                                                                         │
│  → handler extracts the job ID from the URL                             │
│  → calls DynamoDB: "give me the job with this ID"                      │
│  → returns whatever DynamoDB has for that job                           │
│                                                                         │
│  Depending on timing, the user sees:                                    │
│    - status: "pending"    (just uploaded, worker hasn't picked it up)   │
│    - status: "processing" (worker is currently running ffprobe/ffmpeg)  │
│    - status: "complete"   (done — metadata and thumbnail URL included) │
│    - status: "failed"     (something went wrong — error message shown) │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│  GET /api/v1/jobs                                                       │
│                                                                         │
│  → handler calls DynamoDB: "give me all jobs (up to 50)"               │
│  → returns the list with a count                                        │
└─────────────────────────────────────────────────────────────────────────┘

JOB LIFECYCLE — STATUS CHANGES IN DYNAMODB
==========================================

    ┌─────────┐       ┌────────────┐       ┌──────────┐
    │ pending │──────▶│ processing │──────▶│ complete │
    └─────────┘       └────────────┘       └──────────┘
                              │
                              ▼
                        ┌──────────┐
                        │  failed  │
                        └──────────┘

│ Status     │ Set by          │ When                                   │
│────────────│─────────────────│────────────────────────────────────────│
│ pending    │ API handler     │ Immediately after upload               │
│ processing │ Worker          │ When worker picks up the job           │
│ complete   │ Worker          │ After successful processing            │
│ failed     │ Worker          │ If processing errors (no ffmpeg, etc.) │

│           │── 4. Update (processing) ────────────▶│   DynamoDB    │
│           │── 6. Update (complete + metadata) ───▶│               │
│           │◀─ Read jobs ─────────────────────────│               │
│           │                                        └───────────────┘
│           │
│           │                                        ┌───────────────┐
│           │── Send job ID ───────────────────────▶│               │

│           │                                        └───────────────┘

Numbered steps show order for a single job:
  1. API uploads file to S3
  2. API creates job record in DynamoDB
  (API sends job ID to SQS — not numbered because it happens between 2 and 3)
  3. Worker downloads the file from S3
  4. Worker updates status to "processing"
  5. Worker uploads generated thumbnail to S3
  6. Worker updates job with results (status, metadata, thumbnail URL)


KEY DESIGN DECISIONS
=====================

Why interfaces?
  Handlers call methods on interfaces (JobStore, storage.Client, queue.Producer).
  They don't know or care what's behind them. You could swap DynamoDB for
  Postgres, or S3 for Google Cloud Storage, without changing handler code.

Why a message queue?
  The API stays fast — it just drops a message and responds. Processing
  happens separately. If the worker is slow, crashes, or is overwhelmed,
  uploads still work fine. Messages wait in the queue until a worker is free.

Why goroutines?
  Multiple workers process jobs at the same time. The poller and workers
  run concurrently using Go's lightweight threads. A channel connects them
  safely without race conditions.

Why temp directories?
  ffprobe and ffmpeg are command-line tools that read local files. We
  download from S3 to disk, process, then clean up. The permanent copies
  live in S3, not on the server's disk.

Why LocalStack?
  Develop and test without an AWS account, without paying money, without
  internet. Same AWS API, just running locally in Docker. Zero code changes
  to switch to real AWS later.
